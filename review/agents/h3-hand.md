- **Shortcut (.lnk) target reading: UNVERIFIED and not needed here.** Microsoft Learn `IShellLinkW::GetPath` (`learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ishelllinkw-getpath`, ms.date 2018-12-05, read 2026-10-07) confirms: it fills a buffer with the target's path (at most MAX_PATH), returns `S_FALSE` with an empty buffer when there is no path, flag `SLGP_RAWPATH` may return a path that does not exist and holds environment variables; the page does not say how the link object is loaded from the `.lnk` file (I recall `IPersistFile::Load`, **UNVERIFIED**, not built on). The stored pick is the shortcut's own path, so no reading is required. Reading the target is only needed to give such a pick a program file name (open/closed state): the `targetExeName` parameter of `BrowsedProgram` is there for that; without it the tile has no open/closed (subtitle `program`). A shortcut to a Store app, a folder or a document has no exe at all.

- Random id collision (64 bits) is not handled: `Add` would say "not added" as it does for the same thing.
- The refusal reasons for a bad path are plain strings (`PATH_REFUSED`, not in the register): the screen should show them as they are, or the main session adds a register entry.
