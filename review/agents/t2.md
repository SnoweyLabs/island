only; `StopFailure`, `idle_prompt`, `PermissionRequest` do not. `AgentSignals.cs` not touched; a test pins that the

### Version-2 message
`{"v":2,"a":..,"e":..,"k":..,"s":..,"t":..,"f":..,"c":[..]}` + `\n`. Parser: exactly these 8 properties, each once, right
type (`v` integer 2, `t` non-negative integer in int64, `c` array of at most 16 positive ints, texts within limit, `s` may be
empty), whole <= 4096 bytes, depth 3, never throws. A text over its limit is **refused** (the sender cuts), like the old
parser; control/format characters that arrive as JSON escapes are removed from `a`,`e`,`k`,`s` on the way in (the folder is
cleaned later by `ProjectName`). Encoder: cleans, trims, cuts (never inside a surrogate pair), clamps negative time to 0,
and cannot exceed 4096 bytes (worst case checked arithmetically and by a test with 1,000,000-character inputs).

## 4. Not proven / doubts (cautious readings taken)

1. **Equal time at the end.** A message whose time equals the session's end time, arriving after the end, is dropped (the
   work order says "earlier is dropped, later makes it anew"; equal is not said). Pinned by `Session_End_Removes_It...`.
2. **By-name sessions** are made by the caller: `FoundByName(helper, process, chain)`. The tracker cannot decide the
   section-2 exceptions (nearest window owner is an AI program; helper under a helper) because it only gets AI-window owners,
   not terminal windows. T1/the main session decide, then call it at each reading (idempotent).
3. **`aiWindowOwners`** is read as: ids of processes owning a window of an AI program (only those). Terminal windows are
   T1's business.
4. **The helper table** (`helperExeNames`) is a set of file names, not per helper: a Codex session whose nearest helper-named
   process is `claude.exe` would hang on it. Literal reading of the work order.
5. **Replacement of an old id by a new one on the same process** is applied at message time only when the old session's
   process is already chosen; before that, the first process of a chain proves nothing (an AI program's conversations share
   it, and a hook shell differs per message), so two such sessions are settled by the reading that chooses the process
   (newest by sender time, then arrival, stays; an id-less one takes the id and newer state, the older Id stays). The new
   session inherits the replaced one's process.
6. A session is **not shown until the first reading** after its first message (unless its chain holds an AI-window owner).
   If the page is never laid out, sessions are held (<= 64) but never shown.
7. A dropped (late) message still counts as "heard" for the 64-limit; it changes no state, chain or project.
8. A session with no id and an empty chain is keyed `helper|p0`; all such messages are one session.
9. The **steady counter**: `SessionTracker.SystemClockMs()` = `Environment.TickCount64` (documented as ms since the system
   started). Island.Notify must read the same counter (minus the age of its process) or order between v1/v2 is meaningless.
   Not tested against a real Notify (none exists yet).
10. The signal names in T3's tables are text; `TryParseSignal` is lenient, but I never saw T3's strings.
11. Docs: see section 0 (summaries, unknown-event behaviour UNVERIFIED, hooks guide unread).

3. At each reading of the process list (Terminals page only): call `FoundByName` for the helper processes T1 accepts, then
   `ApplyReading(processes, idsOfProcessesOwningAnAIWindow)`; redraw if `Changed`.
4. T1 gets `tracker.Sessions()` (plain `SessionInfo`: chain, project, state, tool name) and asks
   `MostUrgentOf(ids)` for a window with several sessions; the ring colour is the main session's.
