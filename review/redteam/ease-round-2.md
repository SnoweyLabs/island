## 2. The findings

### MEDIUM

**ease-2-1 - the words go stale.** `src/Island.App/IslandController.cs`, `DescribeForScreenReader`. The words are made again only when `var key = (ContentsPageId, selected, items.Count, notice, pill, search, notice ? NoticeText?.Line : playing, SecondRowOpen)` changes. The words contain `items[selected].Title` and `.Subtitle`; the key does not. A tile whose second line changes with the same index and count keeps the old words. Verbatim sources of the changes: `PickPages.ItemsOf` gives "open"/"closed"/"N windows" as the subtitle (cache invalidated by `world.Changed`); `TerminalsPage.ItemOf` gives `tile.SecondLine` (`TerminalsStage` checks `Subtitle.StartsWith("Claude Code")` and a state after a prompt: the state IS the subtitle); the Media tile's second line follows the track. While the island is hidden `Draw` returns (`if (_machine.Phase == IslandPhase.Hidden) return;`) before the check, so the words of the last visit stand at the next summon whenever the page, the selected index and the count are the same: the first tile of Apps, "Alpha, closed, 1 of 6", then Enter starts it, and the next summon says "closed" for a program that is open. What a person would see: nothing. What a screen-reader user is told: a false sentence, on the page whose whole purpose is to say "needs you". Test: source scan of the key line (red: no `items[selected]` in it). Repair (no pixel, no text on screen): add `selected < items.Count ? items[selected] : null` (the record compares by value) to the key tuple.

**ease-2-2 - a second notice is not told.** Same method. The notice is the one thing told as an alert, and its key holds `NoticeText?.Line`, one of two fixed sentences, not `Project`. `NoticeQueue.Post` replaces the notice that is showing when another session's arrives (class comment: "A newer notice replaces the one showing"; `AgentNoticeHost.Tick`: "a newer one replaced it" then `Show(notice)`, which sets `NoticeText` and calls `SetNotice(true)` again). Two helpers that finish within the notice's seconds: the second has the same line, a different project, the key does not change, `Describe` is not called. Run: `Round2ScreenReaderTests.A_Newer_Notice_Of_Another_Project_Replaces_The_One_Showing_And_Has_The_Same_Line` (green, the premise). Defect test red. Repair: `NoticeText` (the whole record) instead of `NoticeText?.Line` in the key.

**ease-2-6 - the way back for a pick is half a way.** `SettingsSession.SetPick`/`ApplyPicks` -> `ReleaseKeysOfMissingPicks`. Round 1's ease-1-3 said the key a person set on a pick goes with it. 19a61f0 keeps a faint chip so the pick can be switched on again; the key is let go when the pick goes (`While_A_Pick_Is_Off_Its_Key_Is_Let_Go`, green) and is not given back when the pick comes back (`Defect_A_Pick_Switched_Off_And_On_Again_Gets_Its_Key_Back`, red: `PickKeyFor(id)` is empty). The chip says "off. Press to switch." and the person set that key themselves; no word says it is gone (`ReleaseKeysOfMissingPicks` warns only when a key cannot be let go). The same holds for a starter pick (older, unchanged). Scenes are fine (`A_Scene_Keeps_The_Pick_Through_Off_And_On`, green). Repair: remember the key with the faint row (`_switchedOff` holds the `Pick`; hold `(Pick, HotkeyCombo?)`), and on `on: true` assign it again when it is still free (`KeybindEditor.Assign`), else say in the notice that the key was taken. Or one sentence on the chip's name when the pick has a key ("its key will be gone").

**ease-2-7 - one odd name hides every pick.** `src/Island.Core/Picks/Pick.cs` `IsStorable` (b34a7d5 added `BlankText.HasBrokenCharacter(Name)` = U+FFFD) and `PickStore.TryReadPick`, which calls `IsStorable` for every pick at load and answers `Unreadable(...)` for the first that fails. A picks.json written by an earlier build that holds a pick with U+FFFD in its name (round 1's own code-1-16: a lone surrogate was storable and came back as U+FFFD; a program name that passed through a lossy conversion has it too) now loads as `Unreadable`: `Parse` returns the empty store, the screen locks the file ("fix it or delete it"), the island starts with no picks. Reach is small (the character must be in the name); the effect is every pick. `Defect_One_Pick_With_A_Replacement_Character_In_Its_Name_Makes_The_Whole_Picks_File_Unreadable` (red: Unreadable, expected Loaded with 2 picks); control green. Repair: the half-character rule is for what is added, not for what is read: in `TryReadPick` call a variant of `IsStorable` that skips it (or replace U+FFFD by `?` in the name at load). The same rule's other side, not tested: a pick with such a name already on the island cannot be moved either (`PickStore.Move` checks `IsStorable`) and is told "cannot move".

**ease-2-11 - the island's selection may never be spoken (UNVERIFIED).** `Visuals/IslandRoot.cs` `Describe`: `RaisePropertyChangedEvent(NameProperty)` for every change, `RaiseAutomationEvent(LiveRegionChanged)` only when `alert`. The root is a `Group` that never has the keyboard focus (the window is `WS_EX_NOACTIVATE`, `Focusable = false`, the keys come as raw window messages), so a screen reader that speaks only the focused element and live regions says "Island" on summon and nothing when the arrow keys move the selection. Whether Narrator speaks a name change of a `Polite` live region without the event is not on the Learn pages I could read (`AutomationProperties.LiveSettingProperty` and `AutomationEvents` only define their names; `AutomationEvents.Notification` exists). Needs Narrator or a person: summon the island with Narrator on, press Right: is the new tile spoken? Repair if not: raise `LiveRegionChanged` for the polite case too (delete `if (alert)`), or `RaiseNotificationEvent` (not verified: the page was not read).

### LOW

**ease-2-3 - the second row is not named.** The key holds `SecondRowOpen` but not `SecondRowSelected`, and the words read `items[selected]`, the + tile ("add something"), the whole time the keyboard is in the row (`IslandMachine.EnterSecondRow`, `MoveSecondRow`; Enter adds the selected row tile). A person who cannot see the row does not know what Enter adds. Adding by hand in Settings is the other, reachable way. Repair: while `SecondRowSelected >= 0` the words name that tile (`_view.Contents` has the row's tiles) and the key holds the index. (Search: `Island, search` is all the words say; its matches are `TextBlock`s that a reader may reach: not checked.)

**ease-2-4 - "Now playing" when paused.** `pill` branch: `$"Now playing: {playing}"`; `PillContent` has `IsPaused` and the pill draws the paused state; the key and the words do not hold it. Repair: `view.IsPaused ? "Paused: " : "Now playing: "` and `IsPaused` in the key.

**ease-2-5 - a removed page's faint chip appears on the next page.** `SettingsSession._switchedOff` is matched by `PageId`; `PageStore.NextId` gives the first free `page-N`. Switch a hand-added pick off, remove its page (the question counts only the picks that are on), make a new page: same id, and the pick of the removed page shows as a faint chip that puts it on the new page when pressed (red test; `Assert.Equal(old.Id, fresh.Id)` in it is the premise). Repair: `DeletePage` removes the page's entries from `_switchedOff` (one line).

**ease-2-8 - the Blur note is false for Darker.** `GlassSection.Build` shows `SettingsText.BlurUnavailable` whenever Blur is not available, whatever is chosen; since e458a67 that is the register's message, whose second sentence is "Island uses the Approved glass instead." True when Blur was the saved choice and fell back; false for a person who chose Darker (`EffectiveGlass` is Darker; red test). Repair: show the sentence only when `Settings.Glass == Blur`, else the first and third parts only (a text that is false is a defect by the one rule).

**ease-2-9 - the steppers do not say their value.** `GeneralSection.IdleCard`/`NoticeCard` `Step`: name "Shorter idle time"; the value label is not focusable and is built again after each press, and the keyboard goes back to the same button. A screen-reader user pressing it hears the button's name again. Repair (no pixel): name `$"Shorter idle time, now {seconds} seconds"` (and the same for the three other buttons).

**ease-2-10 - the fall-through is a button that closes Settings.** `SettingsView.Rebuild`: `(FindByKey(keep) ?? FindByKey("foot:next"))`. After the minus of Idle time reaches 2 s (or the plus 60, Notice time 3 and 30) the control is disabled, `FindByKey` skips it (repair of ease-1-5, held) and the keyboard goes to Continue, which on the last section (General) is Done. A held Enter, or one press too many, closes the whole screen; in Key it moves to the next section. The red test builds General, presses the minus to the end and takes the same target as `Rebuild` (`foot:next`). Nothing is lost (every change is saved at once). Repair: the fall-through is the first enabled control of the same row or card, then Continue.

**ease-2-12 - Esc in the Move list (UNVERIFIED, needs a person).** `PicksSection.MoveControl` makes the `Popup` in code with only a `PlacementTarget`; it is never put in the logical tree. The settings window handles Esc in `PreviewKeyDown` (`SettingsScreen.OnKey`: `HandleEscape()` else `BeginClose()`; `HandleEscape` knows nothing of the list). If WPF routes a key from a popup's content through the owner window, the window sees Esc first (tunnelling) and closes the whole screen, and the list's handler, the repair of ease-1-2, never runs; if the route stops at the popup (no logical parent), the list's handler is alone and the repair holds. The Learn page for Popup says the child stays the logical child of the Popup and does not decide the route. The person's check: open Settings, On the island, Move, press Esc: only the list must close. Repair that does not depend on the route: the view keeps a flag "a Move list is open" that `HandleEscape` uses (and that `MoveControl` sets and clears).
