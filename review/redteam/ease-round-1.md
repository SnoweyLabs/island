## 2. The findings

Anchors are file and member, not line numbers. Repair = smallest.

### HIGH

**ease-1-1 - the island is invisible to a screen reader.** `src/Island.App` (all of `Visuals/`: `IslandView`, `TileView`, `PillView`, `SearchView`, `NoticeView`, `StripView`, `Layers.cs`) and `OverlayWindow.cs`. Evidence: the test scans every `.cs` of `Island.App` (except the self-test's reader `SettingsStage.cs`) for `AutomationProperties.`, `AutomationPeer`, `OnCreateAutomationPeer`: none. The
only `AutomationProperties` in the whole solution are in `Island.SettingsUi` (and `AutomationId` in `AddonText`). The island is custom-drawn (`Canvas`, `FrameworkElement`); its window has no title. What a person would see: nothing changes. What a blind person gets: an unnamed window with no content: which tile is selected, what is playing, that a notice appeared. The island's own keys (Left, Right, Enter, Tab, Delete) work, so a sighted keyboard user is served; a screen-reader user has no island.
Repair: `OnCreateAutomationPeer` on the island's root giving the window the name "Island"; the selected tile a name ("Spotify, Media, selected") raised through `RaiseAutomationEvent` when the selection moves; the notice as a live-region text. Class: safe improvement (no pixel, no movement, no text on screen), large.

**ease-1-2 - a pick cannot be moved to another page without a mouse.** `src/Island.SettingsUi/PicksSection.cs`, `MoveControl`. The small "Apps ▾" button opens a `Popup` (`StaysOpen = false`) and nothing moves the keyboard into it; the method has no `Focus()` call. A Popup's content is not in the tab sequence of the window it hangs from, so Tab goes to the next control and the popup closes. Nothing else in the screen moves a pick. Not run (a Popup is a window; this attacker never shows one): the behaviour of Popup is UNVERIFIED at run time, the finding is from the code. Test: `Defect_The_Move_To_Another_Page_Menu_Takes_The_Keyboard_When_It_Opens` reads the method and finds no `.Focus()`.
Repair: after `menu.IsOpen = true`, `Dispatcher.BeginInvoke(() => list.Children[0].Focus())`, arrow keys between the entries, Esc closes the menu only (as `HandleEscape` does for the Add panel). Looks the same.

### MEDIUM

**ease-1-3 - "switch off" deletes a hand-added pick.** `PicksSection.Chip` (name: "X: on the island. Press to switch.") over `PicksOnIsland.RowsFor`/`Switch`; the first-start words say "Tap to switch any of them off". For a starter pick it is a switch (a faint chip stays). For a program, folder, site or file the person added, the pick is removed and no row is left (the class comment says so: "a pick that is not on the starter list and was switched off is gone"). No question, no way back. What a person would see: the chip vanishes. Test (Core only, no window): `Defect_A_Hand_Added_Pick_Switched_Off_Can_Be_Switched_On_Again` (held beside it: `A_Starter_Pick_Switched_Off_Stays_As_A_Faint_Row_And_Comes_Back`). A key set on the pick and its place in a scene go with it (a scene keeps it as "not on the island now", a pick's key is released). Repair: ask the one-line question first when the pick is not a starter pick ("Remove X from the island? It was added by hand; to get it back add it again with Add..."), as removing a page does; or keep an off row for it. I would grade it HIGH if the person had set a key and put it in scenes.

**ease-1-4 - "Restore the original keys" asks nothing.** `KeySection.RestoreAll` -> `SettingsSession.RestoreAllKeys` -> `KeybindEditor.RestoreDefaults`: clears the main key's change and every page, pick, scene and mode key. Test: `Defect_Restore_The_Original_Keys_Asks_Before_It_Clears_Every_Key_The_Person_Set` (two page keys set, the link pressed, no question open, both gone). Repair: `host.Ask("Take away the keys you set for ... ?", "Yes, restore them", ..., "No, keep them")` with the count.

**ease-1-5 - the keyboard is lost after a control disables itself.** `SettingsView.Rebuild`: `(FindByKey(keep) ?? FindByKey("foot:next"))?.Focus()`. `FindByKey` finds the control with the same key even when it is now disabled; `Focus()` on a disabled element does nothing; the fall-back to Continue is used only when nothing is found. Hits: "Restore default" (after pressing it), "Clear" of a key, the minus of Idle time at 2 s, the minus of Notice time at 3 s, the plus at 60 s / 30 s: a person holding Enter on a minus loses their place and Tab starts again at the top (UNVERIFIED which element WPF then chooses; it is not the control). Tests (both from the code path, through reflection on `FindByKey`, no focus needed): `Defect_The_Keyboard_Is_Not_Sent_To_A_Control_That_Has_Just_Disabled_Itself`, `Defect_The_Keyboard_Is_Not_Lost_After_Restore_Default_On_The_Main_Key`. Repair: take the first match that `IsEnabled`, else `foot:next`. Same look.

**ease-1-6 - three text fields show no mark of focus.** `Parts.QuietBoxTemplate` has no trigger; used by the page colour field (`hex:`), the program-list narrowing field (`add:filter:`) and the site field (`add:site:`). A person who Tabs into one sees only a caret (the field's hairline stays `CapLine`). Every button has the white ring; a page's name box tints its fill by code (12% of the page colour). The one rule's fourth case: the mark a focused control already has elsewhere (the ring of `Parts.PillTemplate`) goes on, and the picture under OWNER DECISIONS. Test: `Defect_The_Text_Fields_Show_No_Mark_Of_Focus_Beyond_The_Caret`. Repair: a `Trigger Property="IsKeyboardFocusWithin"` in the template that sets `BorderBrush` to `#E6FFFFFF` (2 px). Dan would see: a white outline on the field while he types in it.
Also (not tested, a person): the name box's 12% tint on focus is very faint on glass: a proposal to strengthen it with the same ring.

**ease-1-7 - BLUR_UNAVAILABLE in Settings lacks two of its three parts.** `SettingsText.BlurUnavailable` = "Blur is not available on this computer right now." is shown in the Glass section and as the refusal of `SetGlass`; the register's `Refusals.BlurUnavailable` says what, why (Island uses the Approved glass) and what to do (turn on Transparency effects in Windows Settings, Colours, then pick Blur again). Repair: use `Refusals.BlurUnavailable.Message` in `GlassSection` and `SettingsSession.SetGlass`. (The other one-line refusals of `SettingsText` and `SceneText` - `PageNameEmpty`, `NoSuchPage`, `IdleNotUsable`, `NeverOverFull`, `PageLimit`... - give the what and imply the rest; they are not in the register and I did not class them as defects.)

**ease-1-18 - "Show animations" off is honoured by the working ring only.** `SystemParameters.ClientAreaAnimation` is read in `Visuals/TileView.cs` (WORK-ORDER-11's ring) and nowhere else (test `Windows_Show_Animations_Is_Read_In_One_Place_And_Only_The_Working_Ring_Obeys_It`). **ease-1-21 - after "No", the keyboard is on nothing.** `ConfirmOverlay.Close` / `SettingsView` (`_overlay.Closed += () => _layout.IsEnabled = true;`).
