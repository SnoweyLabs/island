## 2. The findings

### MEDIUM

**ease-3-1 - the second row's words give the wrong key.** `IslandController.DescribeForScreenReader`, the `rowTile is not null` branch: `$"Island, {page}, open now: {rowTile.Title}, press Enter to add it, {n} of {count}"`. In the second row `IslandKeys.Enter` answers `SecondRowJump` for Enter and `SecondRowAdd` only for Shift+Enter (run: `In_The_Second_Row_Enter_Jumps_And_Only_Shift_Enter_Adds`, green); `ContentsLayer.ActivateSecondRowTile` is documented "jump to it, add nothing"; the settings screen's own key help says "[Shift+Enter] in the second row adds the thing to the page". What a person who cannot see the row is told: the wrong key for the one thing the row is for. He presses Enter and the island brings that program's window forward (or hides to it) instead; adding by the second row is never reached by following the words (adding by hand in Settings stays). Nothing is lost. Repair (no pixel, no screen text): "... open now: Alpha, Enter goes to it, Shift+Enter adds it, 1 of 3".

**ease-3-3 - search is mute.** Same method, `if (search)`: `_view.Describe("Island, search", alert: false)`; the key holds only the flag `search`. `SearchSession.Push` builds `SearchViewData(Text, Tiles, Selected, ..., Title, Subtitle ("Enter to open"), ServiceTiles)` for the screen: the typed text, how many things were found, the selected one, "Nothing found", "Type to search". None of it is in the words and nothing is told again when the text or the selection changes. Search is opened by typing any letter, so a person with a screen reader who types one is told "Island, search" once and is then in a mode where Left and Right choose among things he is never told, and Enter starts the chosen one (a program or a site). By the letter of the grades this is a whole feature unusable for someone (HIGH); I grade it MEDIUM because every tile is still reachable by the arrows and Enter without search. Repair (no pixel, no screen text): in that branch `$"Island, search, {data.Title}, {selected + 1} of {data.Tiles.Count}"` (or "Nothing found"), and `_searchData` in the key. The typed text is the one thing I would not put in the name: the island's own comment says what is typed "is never passed to a logger, a file or a snapshot", and a name is readable by any automation client; the match and the count carry what a person needs.

**ease-3-4 - the next visit is not told (UNVERIFIED without Narrator for the second half).** Two parts.
(a) `Draw` now resets `_describedKey = default` in its hidden branch. On the ordinary way out `Step` ticks the machine, sees the phase hidden, calls `Detach()` and returns BEFORE it calls `Draw` (`The_Frame_Step_Detaches_And_Returns_Before_Draw_When_The_Island_Is_Hidden`, green); `Detach` does not reset the key. So what the key does not hold stands at the next summon. A closed/open/windows-count change of the selected tile IS in the key (held, through the whole `Item`); what is not in it is the page's NAME (the key holds the page id): rename a page in Settings, summon on the same page, tile and count, and the words still name the old page. LOW.
(b) Even if the reset were reached, `IslandRoot.Describe` returns at once for the same text, and nothing else ever forgets `_description`. The commonest summon is the same page and first tile as the last visit: the words are the same, no name change and no live-region event is raised, so the person is told only the window's own name ("Island"). The comment of the repair ("the next visit is told again") is not what the code does (`Defect_The_Same_Words_At_The_Next_Summon_...`). Whether Narrator also reads the content of a window that has just taken the keyboard I could not test: MEDIUM until a person says it does. Repair: `_machine.ContentsPage.Name` in the key; `IslandRoot.Forget()` (sets `_description = Name`) called by `Detach` together with `_describedKey = default`.

**ease-3-6 - the question is not told (UNVERIFIED).** `ConfirmOverlay.Ask`. It is the only guard before removing a page and its picks, bringing a starter list back, restoring the original keys, deleting a scene, connecting or disconnecting a helper. The keyboard goes to the No button, whose name is "No, keep them"; the question is a `TextBlock` inside a `ScrollViewer` (`Focusable = false`) in a plain `Grid`: no dialog, no name, no help text on either button (`The_Keyboard_Goes_To_No_And_The_Words_Of_The_Question_Are_In_A_Text_That_Cannot_Take_It`, green; the defect test collects the name, help text and labelled-by of both buttons and every ancestor and finds none of the question). A screen reader that says what has the focus says "No, keep them, button". Nothing is lost by accident (No is first, Esc is No), but the person cannot make an informed Yes: "The 5 keys you set ...", "3 picks go with it" are never told. Repair (no pixel): `AutomationProperties.SetHelpText` of both buttons to the question text (a name or a help text is what a screen reader reads with the focused control; which of the two Narrator reads is UNVERIFIED, set both).

**ease-3-13 - the new section is not told (UNVERIFIED).** `SettingsView.Section` setter -> `Rebuild("foot:next")`: the page and the foot are built again and the keyboard is put on the new Continue button. Its name is the same ("Continue"; in the first start "Start", "Continue", "Done" only at the ends); the heading and the sentence are plain texts that never take the keyboard and are not a live region. A screen reader says "Continue, button" after every press and nothing of what the section is; the steps at the top (named "..., current" by ease-1-10) are only read if he goes there. Repair (no pixel): the Continue and Back buttons carry the new section's heading and sentence in their help text (or name them "Continue, next: Your pages"), or the heading becomes a polite live region (the notice line of the same screen already is one).
